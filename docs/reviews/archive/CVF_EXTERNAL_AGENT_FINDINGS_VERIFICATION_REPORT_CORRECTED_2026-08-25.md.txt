## 2. F1 — Corrected: A Live Write Route Exists

### 2.1 What the original report claimed

> "The durable store is an exported, constructible API surface. No live write
> path was traced."

### 2.2 Why that was wrong

`EXTENSIONS/CVF_v1.6_AGENT_PLATFORM/cvf-web/src/app/api/memory/write/route.ts`
exists as a sibling of the `readout` route this author did inspect. Verified:

| Line | Fact |
| --- | --- |
| 3-11 | imports `createFileBackedDurableMemoryStore` from `cvf-learning-plane-foundation/web-runtime` |
| 24 | `provenanceScore?: number;` — optional in the HTTP request body |
| 164, 171, 176 | route requires `verifyServiceTokenRequest` or `verifySessionCookie`; `401` otherwise |
| 202 | `if (!body.actorAuthorized \|\| body.policyDecision !== 'allow')` — both fields are **caller-supplied in the same request body** and the route trusts them for its own policy gate before ever reaching the store |
| 221 | `const store = createFileBackedDurableMemoryStore(storePath);` — **actual construction, not re-export** |
| 230 | `provenanceScore: body.provenanceScore` — passed through unchanged, may be `undefined` |

That value then reaches `durable-memory-store.ts:249` (`?? 1`) and is persisted
at line 287 — exactly the mechanism the original report described as
theoretical.

The line-202 fact matters beyond precision: the route's own admission gate
(`actorAuthorized`, `policyDecision`) is itself caller-declared, not derived
from session/token identity. This means the same request that supplies the
missing `provenanceScore` also supplies the claim that it is authorized and
policy-approved — two self-declared fields feeding one gate, one omitted field
silently upgraded to maximum trust by the store beneath it.

### 2.3 Root cause of the original error

This author's original search was `grep -rln "durable-memory-store" EXTENSIONS/`
— an **importer search**, not a **directory listing** of the API surface. The
`readout` route was found and inspected; its sibling `write` route was never
listed. Finding one route in a directory is not evidence of the absence of a
second one.

### 2.4 Corrected finding

> The durable-store fail-open default is reachable through an authenticated
> HTTP write route (`api/memory/write`) when the durable-store environment path
> is configured. Deployment and external network exposure of that route remain
> unverified by this report — see §8.

Severity: **P1, reachable** (was: P1, theoretical/pre-activation). The
authentication requirement is real and matters — see §2.5 — but it does not
reduce this to pre-activation.

### 2.5 What authentication does and does not establish

An authenticated caller (valid session or signed service token) can write a
record with omitted provenance and have it persisted at maximum trust. This is
not an open, unauthenticated poisoning endpoint. It is a case of an
authenticated actor's *incomplete* input being silently upgraded to *maximum*
attested input — the system, not the caller, manufactures the missing evidence.
This is the same defect shape as the RFR-R7A self-attestation finding
(R7A-F2), applied to a different seam.

## 3. F2 — New Finding: Fail-Open Default Reaches The Provider System Prompt

Neither the external agent nor this author's original report found this. Per
§9, its severity is rated P1, the same tier as F1 — the provider-claim drift in
§6 remains the sole P0. What makes F2 the **highest-priority runtime finding**
is not a higher severity tier than F1, but that it is the only finding in the
entire chain with a verified path to provider-facing content, which should
drive remediation sequencing (§10) even though it does not outrank the P0
outward-facing claim defect on severity alone.

### 3.1 The mechanism

`EXTENSIONS/CVF_v1.6_AGENT_PLATFORM/cvf-web/src/lib/aif-memory-reinjection.ts`:

| Line | Fact |
| --- | --- |
| 99 | `if ((item.provenanceScore ?? 1) < threshold)` — a **second, independent** fail-open provenance default, structurally identical to `durable-memory-store.ts:249` |
| 103-136 (per adversarial review) | items passing the threshold are placed into a prompt block |
| 149-150 (per adversarial review) | the block becomes a governed reinjection system-prompt fragment |

`EXTENSIONS/CVF_v1.6_AGENT_PLATFORM/cvf-web/src/app/api/execute/route.ts`:

| Line | Fact |
| --- | --- |
| 746 | `evaluateAifMemoryReinjection(body.aifMemoryReinjection)` |
| 753 | `enrichedSystemPrompt = aifMemoryReinjection.promptBlock ? buildAifMemoryReinjectionSystemPrompt(...) : ...` |
| 790 | `executeAI(routedProvider, routedApiKey, filteredPrompt, { ...(enrichedSystemPrompt ? { systemPrompt: enrichedSystemPrompt } : {}) })` |

This is a complete, traced path: **omitted provenance → treated as maximum
trust → included in a prompt block → becomes the provider system prompt →
sent to the provider.**

### 3.2 Why this is worse than the F1 write-path finding

F1 establishes that bad data can be *persisted*. F2 establishes that
data admitted under the same fail-open logic can *reach the model*. F1 is a
storage-integrity defect; F2 is the storage-integrity defect **plus** a
demonstrated influence path on provider output. This is the finding that
should drive remediation priority.

### 3.3 Non-claim

`rawMemoryReleased=false` on the *readout* route (verified in the original
report, §6.1) does not bound this path — the reinjection path is a different
route (`execute`) with a different mechanism (`aifMemoryReinjection`, not the
readout candidate list). This report does not claim raw memory content is
released; it claims a *summary derived under a fail-open trust default* reaches
the system prompt. No live invocation was performed; no provider call was
traced beyond static source reading.

## 4. F3 — Corrected: GC-022 Is Active

### 4.1 What the original report claimed

> "The only GC-022 artifacts present are under `docs/baselines/archive/`... GC-022 is the wrong owner to edit."

### 4.2 Why that was wrong

Verified directly:

  `CI_REPO_GATE`.

### 4.3 Root cause of the original error

The original search was `find . -iname "*GC022*" -o -iname "*GC-022*"` — a
**filename** search. The active control lives under
`governance/toolkit/05_OPERATION/` in a file whose name does not contain the
string `GC022` or `GC-022`; only the file's *content* declares the control ID.
A filename search cannot find a control identified by content.

### 4.4 Corrected finding

GC-022 is an active governance control owning **durable-memory record
classification**. It is not archived. It does not own retrieval admission,
runtime write authorization, or TruthReference semantics — those are separate,
currently unidentified or partially-identified owners. Any memory-language
alignment work (Tranche D in the original proposal) must target GC-022's active
surfaces (`CVF_MEMORY_GOVERNANCE_GUARD.md`,
`CVF_MEMORY_RECORD_CLASSIFICATION.md`) and reconcile with, not bypass, them.

P2 rating for `auditTrust` should be read as **route-specific**, not as
