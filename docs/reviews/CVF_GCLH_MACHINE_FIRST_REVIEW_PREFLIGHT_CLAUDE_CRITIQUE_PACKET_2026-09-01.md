## Required Critique Method

Use minimal sufficient verification rather than repeating the roadmap author's
work:

1. verify target identity and current status;
2. inspect the actual existing owner/helper/checker seams;
3. challenge each architecture claim against those sources;
4. construct failure scenarios for the proposed receipt, cache, verifier trust
   and exception-focused readout;
5. distinguish deterministic defects from semantic-review questions;
6. return one consolidated finding set, not sequential drip findings.

Do not rewrite the roadmap. Proposed replacement language or schema fragments
may be included in the critique, clearly labeled advisory.

## Required Review Questions

1. Is a new Phase Return interface owner justified, or would it duplicate
   current owners?
2. Which machine checks improperly cross into semantic truth or value judgment?
3. Does the receipt bind enough - and only enough - to prevent stale or replayed
   acceptance?
4. Can a worker still influence the verifier/config/fixture used to accept its
   own return?
5. Is verifier-set digesting feasible with current autorun catalogs and dynamic
   commands?
6. Does the cache model have a safe, affordable invalidation boundary?
7. Could exception-focused readout hide a material claim or create automation
   bias?
8. Are always-on versus phase-specific packs correctly split?
9. Is historical replay/canary evidence sufficient to support activation?
10. Which metrics measure real savings without creating ceremony or gaming?
11. Are rollback and reactivation rules operationally credible?
12. What should be removed, simplified, added or reordered before P1?

## Required Failure-Mode Analysis

Return at least the three strongest concrete failure modes. Each must name:

- the attacked assumption;
- relevant CVF source path/symbol/section;
- a concrete failure sequence;
- why existing guards would or would not catch it;
- minimal corrective action;
- whether it blocks P1, P2, activation only, or does not block.

Mandatory threat probes:

- verifier changed in the same batch it accepts;
- stale receipt after checker hardening;
- cache hit across a hidden dependency/environment change;
- manifest under-declaration;
- authority path resolves but semantic owner meaning is wrong;
- helper filters out the one material exception;
- machine PASS induces reviewer automation bias;
- machine layer costs more than the reviewer work it removes.
