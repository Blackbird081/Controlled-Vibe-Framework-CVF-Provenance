### Executive technical conclusion
At this pin, Unreal Agent has a real durability architecture, but its supported guarantees are narrower than an end-to-end exactly-once runtime. The strongest source-backed mechanisms are: append-only session history; durable, versioned operation checkpoints; restart recovery of nonterminal and unsettled terminal operations; caller-ID deduplication for **persisted external inputs**; write-ahead persistence before LLM/tool dispatch; actor-serialized local operation management; and append-tail recovery. The source does **not** support a blanket exactly-once input, provider, operation, or external-side-effect guarantee. Same-session store calls are explicitly not serialized by the Store contract, LocalOperationManager at-most-once is explicitly scoped to the manager lifetime, and provider retries can issue multiple requests.

### Delivery semantics in one sentence
**Overall delivery semantics are not specified as exactly-once/effectively-once.** The implementation provides in-process at-most-once Inbox emission by input ID and restart deduplication for already-persisted external IDs, but `Inbox.Submit` can succeed before `AppendInput`, leaving a crash window that requires caller redelivery.

### Determinism boundary
`Resume` reconstructs persisted history and operation checkpoints, but **full re-execution is not deterministic**: provider retries/reissues can occur, fresh turn IDs may be generated, and operation/remote external effects depend on operation-specific semantics. No blanket deterministic replay or exactly-once recovery contract is supported.

## Operation-manager contract and durability boundary
The operation manager is an **actor runtime over serializable/versioned operation values**, not itself the durable store. `Operation` carries Type, Version, Status, JSON State, and JSON Idempotency; `Step.Operation` is explicitly the next durable checkpoint. `Manager.Add` promises at-most-once start **only for each ID during the manager's lifetime**. Durability is supplied by coordinator/session-store persistence of initial operation snapshots and later `SaveOperation` checkpoints. On restart, `ResumeState.Operations` are fed to a fresh manager; ready/awaiting/canceling operations are re-dispatched, while terminal-but-unsettled states are retained for reconciliation rather than ordinary dispatch.

Remote jobs are an interface-level extension with concrete type/version/state validation: `RemoteJobPlan` and `RemoteJobState` are serializable and versioned; `RemoteJobHandler` supplies add/cancel/update hooks; incoming updates cannot mutate operation type/version/plan and must obey status transitions. The audit did **not** establish a generic distributed proxy service with proven remote restart recovery or idempotent external side effects at this pin. That stronger claim remains `NOT_FOUND`.

## LLM turn and provider boundary
The coordinator persists an external input before processing it, persists a new `Turn` before starting `LLM.Respond`, and persists the returned normalized `ModelResponse` before scheduling/dispatching tool operations. The Responses adapter owns retry/cancellation/provider-error handling. It can issue more than one provider request for one logical call, retries transport failures/unexpected EOF/retryable provider errors, and resets per-attempt `responseState`; a tested partial first attempt does not contaminate the second. Cancellation propagates through context. A terminal response already observed before transport disconnect is preserved without retry. **The source does not claim and does not implement an exactly-once model-execution guarantee.**
