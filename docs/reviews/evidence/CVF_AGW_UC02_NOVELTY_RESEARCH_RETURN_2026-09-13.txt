B. Clarifications
Regex order and reject/mask precedence (request and response, symmetric): rules in a single RegexRules.rules list are evaluated in order; first Reject/Audit match short-circuits (mod.rs:1791-1831); Mask actions accumulate into a working buffer and continue through all rules (mod.rs:1794-1812, 1832-1852). One RegexRules guard has one action (mod.rs:2049) applied uniformly to all its rules — you cannot mix per-rule reject vs. mask inside a single guard; that requires separate RegexRules guard entries (as config.yaml does: one reject-SSN guard, one reject-email guard, both action: reject).
Response-PII vs. output governance-pattern screening — these are different mechanisms in both systems. In AGW, evaluate_regex_response is one generic mechanism that can carry either PII builtins or arbitrary custom patterns — there's no structural split. In CVF, they genuinely are two different concerns bolted together: UNSAFE_PATTERNS (destructive commands, credential leaks, injection/exploit language) and GOVERNANCE_OUTPUT_PATTERNS (echoed bypass instructions, SAF2) are both folded into the same UNSAFE_CONTENT issue and the same RETRY decision (output-validator.ts:139-152) — CVF has no PII-specific output pattern set at all (no output-side SSN/email/CC detection). This is a second, narrower delta beyond the masking gap: CVF's output validator screens for unsafe/governance-bypass content, not for PII leaking back out in the response.
Streaming/buffering — confirmed from streaming_guardrails.rs:1-18 doc comment and mod.rs:1898-1903: AGW buffers SSE text in windows (default 1024 bytes, 256-byte overlap tail) and evaluates each window; mask is explicitly disallowed for streaming responses (only Pass/Block), and content already flushed in an earlier passing window cannot be retracted — an accepted accuracy tradeoff documented by the authors themselves. CVF's /api/execute route, per the read scope, is non-streaming (aiResult.output is validated as a complete string post-invocation) — so this AGW limitation and CVF's full-buffer validation aren't directly comparable; CVF's approach is strictly more thorough (full output, not a window) but pays for it with the regenerate-or-reject cost noted above.
Webhook payload/header forwarding: by default zero request/response headers are forwarded to the webhook; only headers matching an explicit forwardHeaderMatches allowlist go out (mod.rs:1706-1726, webhook.rs README section). CEL header expressions run against the original client request context (request.*, jwt.*), not the webhook's own request, and a failing expression silently omits that header rather than failing the call (webhook.rs:433-464, confirmed by the module's own test suite for graceful degradation). JWT claims are explicitly never attached to the outgoing webhook request itself (webhook.rs:424-441, with an inline comment noting this is deliberate to avoid leaking the raw JWT to the webhook backend's own auth chain).
Timeout/transport-error/non-success/malformed-response handling: a 10-second default timeout is attached to every guard/webhook outbound call (mod.rs:20-25 with_default_timeout). On any error constructing/sending/parsing the webhook call (timeout, transport error, non-2xx via call_reference, or malformed JSON via json::from_response_body), the single anyhow::Result error path is taken — FailureMode::FailOpen logs a warning and allows the content through unmodified (mod.rs:1533-1541 request, 1629-1637 response); FailureMode::FailClosed (the schema default per webhook.rs's Webhook.failure_mode doc comment) propagates the error up, which fails the whole guard evaluation closed. AGW does not distinguish "webhook timed out" from "webhook returned malformed JSON" from "webhook returned HTTP 500" — all three collapse into the same generic error → failure_mode branch. There is no partial-content-passthrough state; it's binary allow-everything-through (fail-open) or block-the-whole-call (fail-closed).
What leaves the trust boundary: for a webhook guard, the full message list (Vec<Message> — role+content, i.e. complete prompt or complete response text) is serialized to JSON and POSTed to the configured target backend (webhook.rs:149-171, 241-283), plus any explicitly allowlisted forwarded headers and any CEL-computed custom headers. This is a full trust-boundary crossing of user/model content to a third-party service — no CVF consumer currently authorizes or requires this; per the deferred-trigger triage's Risk section, this must not be treated as a free extension of an existing provider connection.
C. If a useful delta exists — bounded adaptation proposal (one only)
Consumer: /api/execute route's output-validation stage (EXTENSIONS/CVF_v1.6_AGENT_PLATFORM/cvf-web/src/app/api/execute/route.ts, output-validator.ts).

Proven requirement: CVF's output path has no mechanism to ship a response with only the offending span redacted — every UNSAFE_CONTENT detection forces a full model regeneration (up to 2x) and, on exhaustion, throws away the entire response via a 422. AGW's evaluate_regex_response demonstrates a working, in-repo pattern for detect-and-mask-in-place on response text without discarding the rest of the response or re-invoking the provider.

Existing owner to receive it: output-validator.ts (SAF2 owner surface) — not a new owner. The adaptation is: add a bounded regex mask step (reusing SAF2's existing UNSAFE_PATTERNS/GOVERNANCE_OUTPUT_PATTERNS match logic, restructured to capture match spans rather than only a boolean .test()) that redacts matched spans in aiResult.output in place, as an alternative decision to RETRY, before the retry loop and before OUTPUT_VALIDATION_EXHAUSTED.

Seam/dependency: requires converting isGovernanceOutputUnsafe/the UNSAFE_PATTERNS.some(pattern.test(...)) calls into span-capturing matches (pattern.exec / matchAll) — a source-code change, not a config change; also requires a new ValidationDecision value or equivalent (e.g., 'MASKED') and a route-level decision on whether masked output still counts toward OUTPUT_SAFETY_TRIGGERED audit semantics.

Benefit: avoids burning provider calls/latency and avoids discarding an otherwise-useful response purely because one span matched an unsafe/PII pattern.

Verification condition before acceptance: a separate reviewed work order with its own source-verified baseline; this proposal is evidence-of-need only, not an implementation authorization. Distinguish this from a hypothesis — the gap (no output masking exists) is proven by direct reads of both output-validator.ts and route.ts; the specific mask-design above is a proposal, not proven-optimal.

Webhook disposition (kept separate per instructions): no adaptation proposed. No named CVF consumer requires delegating content decisions to an external service; this remains DEFER_WITH_TRIGGER.
