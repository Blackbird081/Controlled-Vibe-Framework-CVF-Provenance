## 2. Verdict: REVISE_BEFORE_ACCEPTANCE

The principles are sound and well bounded: authority, method support and quality are kept separate; no score inheritance across versions; unknowns are null, not zero; tokens are not money; history is append-only; the Non coder is not asked for model choice; proof classes are separated; Expense stays parked.

Two owner-composition blockers prevent design acceptance:
- **F1:** selection is bound to Model Gateway owners that do not cover the real use case (operator-started worker seats).
- **F2:** orchestrator model choice is not reconciled with the Role Assignment Matrix rule that the operator chooses topology and model assignment.

Three contract defects (F3, F4, F5) would stall the first real loop or produce misleading states.

- **Design-readiness:** reachable with one grouped revision. No new evidence is needed.
- **Build-readiness (S2):** not ready. F1 must be resolved, and an executable owner for the decision record must be named.

## 4. Rebuttal

**Strongest alternative: manual prototype first, schema later.** The package proposes six record families, a six-state lifecycle and a strict validator (S2) before any real loop (S3). For a process that produces about one decision per tranche, made manually by one orchestrator and one operator, that order risks building the wrong schema.

The alternative:
1. Add a short selection-rationale block to the next real work order: delegation source, candidate dispositions, evidence cited with its compatibility, chosen seat and known unknowns.
2. Append the reviewed outcome to the existing tranche ledger.
3. In a later work order, write a consumption line.

Run two or three real demand-driven tasks this way, then decide whether S2 is worth building, and against which fields. This reuses existing work-order and ledger owners, needs no GatewayReceipt companion or fresh GC-018 for a companion, and still produces actual-use evidence. **Recommended order: S1 review, then S3 manual on surface B, then S2 only if the manual loop shows the fields are needed.** The Spec/WO separation rule does not block this, because the work order records a decision in prose and does not build against an unratified contract.

**Remove:**
- LATER_CONSUMPTION_VERIFIED from the decision lifecycle (F5).
- The GatewayReceipt ownership claim for surface-B decisions (F1).
- Any implication that `provisionalRoleRouting` routes anything (F6).

**Add:**
- The two-surface split (F1).
- The delegation clause (F2).
- The default PROVISIONAL admission rule (F3).
- The EXACT/PARTIAL identity rule (F4).

**Author assumptions rejected:**
- That the Model Gateway admission chain (policy, then isRoutable, then health) is the right gate for worker-seat selection. It is the right gate for API routes only.
- That PLL typed APPLICATION semantics cover model-performance learning. They cover only parent-finding controls.

**Accepted:** hard-filter-first with no weighted compensation; tokens are not money; no score inheritance; null, not zero; reasoned no-change is legitimate; proof-class separation in the roadmap.
